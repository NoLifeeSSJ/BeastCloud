# Security model and review notes

BeastCloud protects against unauthenticated network clients and restricted local accounts. It does not claim to resist a malicious administrator of the server or to provide end-to-end encryption. Ordinary originals are stored as local plaintext blobs; BitLocker is an optional owner-managed protection for powered-off media. Uploaded files are not executed. HTML/SVG/unknown formats are attachments, text is rendered as text, and browser-supported media is served locally with range support. PDF viewing relies on the browser's PDF implementation.

ASP.NET Identity PasswordHasher uses its versioned PBKDF2 format with 210,000 configured iterations. Password inputs are bounded (12–256 characters). Random setup, session, share, device and recovery credentials use the OS cryptographic generator. Sessions/share/device verifiers and recovery-code hashes are stored rather than usable bearer tokens; cookie authentication is never placed in browser localStorage. Local storage holds theme and nonsecret resumable upload IDs only. Session state and CSRF are server-validated; owner-only APIs refuse restricted accounts, and device credentials access only dedicated sync routes/subtrees. There is no email reset, default administrator password or unauthenticated filesystem export.

Optional TOTP uses HMAC-SHA1/30 seconds/six digits and a ±1-step clock tolerance. A confirmed owner-only flow enables it; recovery codes are one-use and reset TOTP. Keep Windows time correct. Authentication, pairing and public share endpoints use a bounded per-IP rate limiter. No forwarded headers are trusted automatically, and deployments behind an owned proxy must account for limiter scope themselves. Password hashes, authenticator seeds, PFX/password configuration and backup contents require restricted disk access. Seeds are protected by the database ACL, not a claim of per-field encryption. Companion secrets use Windows DPAPI CurrentUser; re-pairing is the migration procedure.

Filesystem boundaries validate Windows reserved names (including extensions), separators, control characters, ADS colons, trailing dots/spaces, UNC live roots and reparse/symlink ancestors. Immutable physical blob identities are fixed-format 32-hex values; logical names never choose physical paths. Tree operations reject cycles and case-insensitive sibling collisions. ZIP restores reject escaping paths, links and excessive disk expansion. This is defense in depth with service ACLs; an already privileged local process can race or modify these directories, and is outside the network-client threat boundary.

Uploads reserve staging capacity, enforce exact offsets/length/chunk hashes, never acknowledge whole-file commit before the durable blob and metadata transaction, and preserve originals on version conflicts. Missing managed-volume sentinels refuse access rather than initialize alternate storage. Thumbnails decode only configured uploaded content, at bounded input size/pixels with one worker; arbitrary file content is not sent to an external renderer.

Headers include nosniff, no-referrer, no framing, a restrictive self-only content security policy and HSTS over HTTPS. Production has no HTTP authentication path. Installer PFX/config ACLs and optional certificate trust must be maintained; do not use Development mode or disable TLS validation to make remote access easier. CSP permits inline styles for local React styling, but no inline scripts or outside script/font/connect origins.

Operational logs rotate separately from the append-only application audit table. The application never intentionally logs passwords, full bearer/session tokens, recovery codes or private file contents. Audit may contain opaque item/account IDs and operation names. Logs and backups remain local and should be protected/retained according to the owner's policy. The audit table is not tamper-proof against the owner/administrator.

NuGet/npm vulnerability audits are recorded in VERIFICATION.md; they are time-specific checks, not a guarantee of future dependency safety. Local release manifests are checksums, not signatures. Packaging does not invent a signing identity. Obtain packages from an owned trusted source and verify archive hashes independently. Independent security review and Windows hostile-filesystem/concurrency testing remain recommended before sole-copy use.
